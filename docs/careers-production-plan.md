# Careers: implementation and production gate

Prepared 11 October 2026. User-confirmed architecture: Supabase for vacancies/admins; email PDF CVs to reception@ropeaccess.co.za; do not save CVs on the website. Local implementation only. Publication and live acceptance tests remain separate. No system is vulnerability-free.

## Product and design

Existing Archivo/Inter, electric blue, navy, technical rules and industrial imagery. Careers is a project mobilisation board with honest availability and no fabricated vacancies. Desktop/mobile/drawer/footer links and sitemap; editorial hero; project-team expectations; searchable role board with region/contract filters; expandable descriptions; role-specific application form; four hiring steps; category FAQ adapted from the supplied reference with keyboard-operated tabs and native disclosures.

Each vacancy has a reference, role, level, certification scheme, region, site/town, industry, contract, headcount, duration, start window, working pattern, description, selected and custom requirements. Catalogues include 26 role choices, nine provinces plus cross-border/multiple sites, six contract choices, and 40 selectable requirements. Every administrator catalogue offers Other. Do not interpret IRATA/IWH as automatically interchangeable; requirements must match the actual client specification. Draft → published → closed/archived; optional date expires at 23:59 South African time. Closing removes the role without a rebuild. Optimistic version checking prevents an administrator overwriting another's edit. All vacancy fields are public when published; no confidential notes in this table.

Public disclaimer: a listed vacancy is still accepting applications; listing does not guarantee employment. No unsolicited CV email when there are no adverts. Each role includes the requested Description and Requirements / cover-letter guidance. Apply → Chat → Prove It → Level Up uses industry-specific onboarding and first-assignment wording.

Application: selected role, name, email, telephone/WhatsApp number, preferred contact, current town/province, availability, level, focused cover letter and one PDF up to 5 MB. No applicant account. No talent pool. No ID or medical uploads; mention fitness certification as a requirement and arrange verification privately later.

## Data path: no website CV archive

Applicant browser → bounded server memory → private contracted PDF scanner → Resend → reception@ropeaccess.co.za. The PDF, cover letter and contact details are never written to Supabase Storage, website disk or an application table. No attachment URLs. All email recipients are fixed on the server. Applicant email is only the reply-to. Plain-text email contains role/reference, applicant details, cover letter and advertised requirements, with a randomly named PDF attachment. Stable HMAC-based Resend idempotency prevents identical retries sending repeated emails within the provider's 24-hour window. Acceptance by the email provider is not proof of arrival in reception; monitor deliveries/bounces and test the mailbox before launch. No applicant confirmation email is implemented; on-screen success gives the reference.

The mailbox, outbound email provider, scanner, infrastructure and backups have their own processing/retention behaviour. “We do not keep CVs” means the website has no CV archive; it cannot mean no copies exist while CVs are sent by email. The Information Officer must approve mailbox deletion, recipient access, provider agreements, storage regions and cross-border safeguards. The scanner must not retain/share PDFs; never use a public sample-sharing scanner for personal CVs. Check infrastructure does not capture request bodies or write multipart bodies to disk. Failure exits are generic and do not log personal payloads.

Supabase holds public vacancy content, exact administrator UUIDs, vacancy audit events (actor/action/status/time) and one-hour HMAC identifiers/counters for abuse prevention. Rate counters purge expired entries on the next attempt; configure an additional daily database cleanup if traffic stops. No raw applicant IP/email, CV, cover letter or applicant row is stored there. The current mailbox notice is a draft pending Skyriders privacy sign-off; do not claim a POPIA compliance certification.

## Administrator identity

Provision two separately owned accounts: it@ropeaccess.co.za and beata@ropeaccess.co.za. Disable Supabase public signup. Verify ownership, enrol TOTP in an attended setup, then use `supabase/bootstrap-admins.sql` to pin verified UUIDs into an inaccessible administrator table. Email matching alone grants nothing. Password + Authenticator code on each sign-in. API validates the current user and signed JWT; database checks active UUID membership, exact current email, confirmed account, no current ban, verified TOTP factor, an existing auth session, aal2 and a TOTP verification within eight hours. Revoking membership or removing the auth session blocks subsequent operations even if a token is cached.

Browser sessions use sessionStorage, scoped to the tab. They are still exposed to successful same-origin XSS. The implementation adds frame/object/base restrictions and React escapes all plain text; complete a nonce-based script CSP and staging review before production. No user HTML rendering. Do not grant SQL/service credentials to administrators or place them in NEXT_PUBLIC variables. Only vacancy operations use the user's own token/RLS; the service key is used for the shared limiter and validating open adverts during application submission.

TOTP reduces password-only account takeover but does not prevent phishing, session theft, insecure database grants, malicious attachments, device compromise or leaked service keys. Consider phishing-resistant passkeys/SSO if the selected setup can enforce the required assurance. Configure strong passwords, provider login limits, short JWT lifetime, session limits, SMTP and verified lost-device recovery. Never reset MFA solely on an emailed request. Add project-owner MFA and alerts. Do not share the two accounts between people.

## Upload and abuse controls

5 MB PDF only, enforced while reading the request stream and again on the actual file. Extension, MIME, PDF header and final marker checks are screening, not full parsing or antivirus. A private scanner must reject malware, encrypted/corrupt/uninspectable documents; the server refuses email delivery if scanning fails or is unavailable. Scanner integration contract: authenticated HTTPS POST of raw application/pdf, bearer secret; return JSON `{ "clean": true }` only after complete inspection. No scanner service is provisioned by this repository. Configure and validate it before enabling submissions. Do not bypass the scanner to get a green preview.

Turnstile server validation checks success, expected hostname and action; tokens are single-use. Shared database limiter uses atomic increments (10 requests/hour per HMAC address, 3 accepted attempts/hour per HMAC email). Hosting must overwrite trusted forwarding headers; add edge/WAF limits and a request body cap of at least 5 MB plus multipart overhead. Confirm the hosting platform accepts this size; a 4.5 MB body-limit platform needs a lower advertised CV limit or a separate transient upload service. Bound request duration at the host to prevent slow uploads.

Recheck vacancy availability after scanning. This defines acceptance immediately before dispatch; an application accepted while open may arrive after an administrator closes the role. Email sending and PostgreSQL are not a single transaction. Do not promise that closure recalls in-flight mail. No fake success on errors; keep entered fields for retry; idempotency is scoped to identical application content and role revision. Rate limits can temporarily affect retries and are explained on screen.

## Launch sequence: required acceptance gates

1. Choose hosting and the verified SITE_URL; create staging Supabase and apply the versioned migration. Inspect grants/RLS. Disable signup; configure SMTP/password/session/login limits. Provision and verify the two accounts, enrol TOTP, then bootstrap exact memberships. Test recovery and revocation. Document the privacy/recruitment owner and mailbox handling policy.
2. Connect Resend with a verified recruitment sender and confirm delivery plus attachment to reception. Configure delivery/bounce monitoring. Contract/configure/test the private scanner and Turnstile allowed hostname. Provision server secrets securely; isolate staging from live email delivery.
3. Execute actual Supabase tests as anon, non-admin, allowed-email without membership, admin without MFA, expired/revoked/banned session, removed TOTP factor and MFA admin. Only the last may write/read drafts. Direct REST, not just UI, must obey the same policy. Audit entries must appear; no public application/CV tables or bucket should exist.
4. Test create/edit/Other/draft/preview/publish/close/archive/expired role and competing admin edits. Submit one clean test PDF; confirm role/site/contact/cover/requirements and readable attachment in reception. Test closure during scan, identical retry after a timeout, outdated advert and email-provider error. Confirm no CV files or applicant records remain on the website.
5. Test spoofed extension/MIME, oversize/chunked body, encrypted/corrupt PDF, standard antivirus test fixture, scanner outage, CAPTCHA replay, wrong hostname/action and distributed rate limit. Test at the real hosting edge/body limit. Inspect request-body logging and temp-file behaviour at host and scanner. Do not test with real applicant information.
6. Keyboard/mobile/tablet/desktop/zoom/screen-reader QA; FAQ tab navigation; vacancy selection; errors/retry/success. Lint, typecheck, production build, dependency audit, all internal destinations and assets. Verify production sitemap/canonicals/robots, HTTPS/security headers, admin noindex/no-store and a strict script CSP. Investigate the lint-toolchain audit advisory separately; do not downgrade Next using npm audit --force.
7. Complete Information Officer/content approval, provider agreements, mailbox access/deletion, backups and incident-response exercise. Production deploy only after these tests pass. Nothing has been published by this task.
